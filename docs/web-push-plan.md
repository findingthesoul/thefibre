# Web push for my.thread — plan

Status: **built, dark until the VAPID keys are set** (builder 5, 2026-10-16).
Sjoerd answered §10 on 2026-10-16, all as recommended: quiet hours, a cap of
six, hard delete, the session title on the lock screen, staging first.

## 1. What it is

Sjoerd, 2026-10-14: a follower gets *"a message, email and notification in
their potential webapp"*. The bell and the email exist (`member_notification`,
`lib/member-notify.ts`, v1.23x). This is the third channel: the same bell rows
arrive on a participant's phone or desktop **when they asked for that on that
device**.

It adds no new events. Push carries exactly what the bell already shows,
from the same rows and the same rules: the community switch, the "editing is
not announcing" SEND, the once-ever new-thread rule, and the baseline.

## 2. What exists today (checked on staging 91dfb72a)

- **A service worker:** `apps/my/public/sw.js`, VERSION `v4`. It
  handles the offline shell, immutable `/_next/static`, and ticket QRs. It has
  no `push` handler. `register-sw.tsx` registers it for everyone, signed out
  too.
- **A manifest:** `apps/my/app/manifest.ts`, built with
  `@thefibre/shared/pwa`. Its header comment still says "there is no service
  worker"; that's stale and gets fixed in the same release.
- **`scripts/check-sw-freshness.mjs`** fails a release when a precached file
  is newer than its worker. Push changes the worker but no precached file, so
  the check doesn't force a bump. We bump VERSION anyway, deliberately, see §6.
- **The bell:** `member_notification` has four kinds (`new_thread`,
  `session_added`, `session_moved`, `session_cancelled`). Its `email_state` is
  one of `pending | sent | skipped | none`. The API reaches it with the
  service role only (RLS on, no policies).
- **The job:** `runMemberNotify` (new-thread pass, then the digest) runs
  on the API scheduler under a lease, every scheduler tick (5 min). The email
  digest waits for 15 quiet minutes per person.
- **No push library** in any package.

## 3. Keys (VAPID)

- **One key pair per stack.** Staging and production are separate pairs. A
  subscription is bound to the public key it was made with, so a shared pair
  would let a staging server push to production phones.
- **Generated by Sjoerd**, on his machine, never in a chat:

  ```bash
  npx web-push generate-vapid-keys
  ```

- **Set by Sjoerd** as Fly secrets, typed with `read -s` so the private key
  never lands in shell history:

  ```bash
  read -s VAPID_PRIVATE_KEY && fly secrets set -a thefibre-api-staging VAPID_PRIVATE_KEY="$VAPID_PRIVATE_KEY" VAPID_PUBLIC_KEY=<public> VAPID_SUBJECT=mailto:support@thethread.app
  ```

  Then the same on production with its own pair.
- **The public key reaches the browser from the API**,
  `GET /me/portal/push/config` → `{ publicKey }`. There's no Vercel env var,
  so there is one place to set it, and a web build can never hold a key that
  doesn't match its API.
- **Dark until set.** With no `VAPID_PRIVATE_KEY`, the config route answers
  `{ publicKey: null }`. The button then says nothing at all, and the job skips
  push. This is the same posture as the assistant (dark until
  `ANTHROPIC_API_KEY`).
- **Never rotate casually.** A new pair silently ends every existing
  subscription; each device has to opt in again. Rotation is a decision, not
  maintenance.

## 4. The subscription table (one migration)

One row per device:

```sql
create table public.push_subscription (
  id            uuid primary key default gen_random_uuid(),
  -- The participant's verified email: the key every /me/portal route is
  -- scoped by, and the one identity_profile uses. NOT person_id — person
  -- is per workspace, and a phone belongs to the human, not to one community.
  email         text not null,
  endpoint      text not null unique,
  p256dh        text not null,
  auth          text not null,
  -- "iPhone · Safari", for the list of devices on the You tab. Derived from
  -- the user agent at subscribe time; never the raw UA.
  device_label  text,
  created_at    timestamptz not null default now(),
  last_ok_at    timestamptz,
  fail_count    integer not null default 0
);
create index push_subscription_email_idx on public.push_subscription (email);
alter table public.push_subscription enable row level security;
-- No policies: reached only through the API, like member_notification.

alter table public.member_notification
  add column push_state text not null default 'none'
    check (push_state in ('pending', 'sent', 'skipped', 'none')),
  add column pushed_at timestamptz;
```

- **Default `'none'`.** Every row that already exists stays unpushed, so
  turning push on never replays the backlog. New rows are written `pending`
  only when the person has at least one subscription at insert time. Otherwise
  they're `none`, and no job ever looks at them again.
- **The migration version comes from `./scripts/new-migration.sh`.** It's
  applied to staging with `scripts/db-push-staging.sh`, and the file is pushed
  in the same step.

**Cleanup:**
- A 404 or 410 from the push service means the browser dropped the
  subscription. The row is **hard-deleted** at once.
- A 429 or 5xx is retried on the next tick. `fail_count` goes up and
  `last_ok_at` stays.
- After 5 consecutive failures spread over at least 3 days, the row is deleted.
- Signing out on a device unsubscribes it in the browser and sends
  `DELETE /me/portal/push/subscriptions`.
- Erasure and the Article 15 export include the rows. They are personal data:
  an endpoint identifies a device.

> **Hard delete is a deliberate exception to "soft delete only"**, the same
> one credentials get. A dead endpoint is not a record of anything. Keeping it
> would only mean holding a device identifier we can't use. This one needs
> Sjoerd's yes (§10).

## 5. The API (new route file, not portal.ts)

Everything goes in `routes/portal-push.ts`, mounted beside `portalRoutes`, so
the shared `portal.ts` gets no hunk at all.

| Route | Does |
|---|---|
| `GET /me/portal/push/config` | `{ publicKey }`, or `null` while dark |
| `GET /me/portal/push/subscriptions` | this person's devices: label and created date, never the endpoint |
| `POST /me/portal/push/subscriptions` | `{ endpoint, keys: { p256dh, auth } }` → upsert on endpoint |
| `DELETE /me/portal/push/subscriptions` | `{ endpoint }`, or `{ id }` from the device list |

**The endpoint is an address our server will POST to,** so it's
allow-listed by host before it is stored:
- `fcm.googleapis.com`
- `*.push.apple.com`
- `updates.push.services.mozilla.com`
- `*.notify.windows.com`

Anything else gets a 400. Without the list, `POST /subscriptions` is an SSRF
handle. The allow-list gets a test, including `https://169.254.169.254/` and
a lookalike host.

**Sending:** `lib/web-push.ts` wraps the `web-push` npm package (MIT,
mature, does the RFC 8291 encryption). It's a plain npm dependency, so no
Dockerfile change is needed.

## 6. The device (sw.js) and the button

**`sw.js` gains two handlers and nothing else:**
- `push` → `showNotification(title, { icon: '/icon-192.png', badge, tag, data: { url } })`.
  The `tag` is per thread, so a second change to the same thread replaces the
  first on the lock screen instead of stacking.
- `notificationclick` → focus an open my.thread window and navigate it,
  or `clients.openWindow(url)`. **Only same-origin paths are opened.** A
  payload URL to anywhere else is ignored, so a bad payload can't send a phone
  to a phishing page.

The worker is sticky, so the change stays this small. VERSION goes to `v5`.
That isn't because the check demands it: a deploy that changes the worker
should be visibly a new worker in DevTools when somebody debugs a phone.

**The button: never a prompt on page load.** Browsers penalise it, iOS
refuses it, and it's rude. The control lives in **builder 3's Notifications
tab on You** (`/you?tab=notifications`), below the existing email switch. I'll
build it as one client component, `push-card.tsx`, which builder 3 places.
Agreed with builder 3 (2026-10-16): `NotificationsPanel` in
`apps/my/app/you/page.tsx` renders `<CalendarCard />` then `<NotifyCard />`,
with a slot right after `NotifyCard`. `<PushCard />` takes no props. Whoever
lands `push-card.tsx` adds the one import and the element there, after
pinging builder 3. It has four states:

| State | Shows |
|---|---|
| unsupported (no `PushManager`) | iPhone/iPad in Safari: "Add my.thread to your Home Screen first, then turn this on there", linking to the Help guide. Elsewhere: "This browser can't show notifications." |
| not yet asked | **Turn on notifications on this device** → `Notification.requestPermission()` inside the click, then subscribe, then POST |
| on | "On for this device" · Turn off. Below it: other devices, each with Remove |
| blocked | "Notifications are blocked for my.thread in this browser's settings." No button: only the user can undo a deny |

The `/notifications` page gets one quiet line pointing at the tab, shown only
when this device isn't subscribed. All strings go in `apps/my/lib/i18n.ts`,
in six languages.

## 7. What pushes, and when

| Kind | Pushed? | When |
|---|---|---|
| `session_cancelled` | yes | next job tick (≤5 min) |
| `session_moved` | yes | next job tick |
| `session_added` | yes | next job tick |
| `new_thread` | yes, **batched** | after the same 15 quiet minutes as the email; one push per community: "3 new on the Choir calendar" |

- **Batching.** Session changes come from one organiser SEND, so one SEND
  is one push per person per thread ("2 sessions moved: Choir rehearsal").
  New threads arrive in bursts (an organiser loading a year), so they wait for
  the quiet window, exactly as the digest does.
- **Circuit breakers.**
  - The existing `HOLD_ABOVE` holds a mass publish, and held rows push
    nothing until an admin announces them.
  - A new cap: **at most 6 pushes per person per day**. Over that, rows go
    `skipped` and stay in the bell.
- **Quiet hours (proposed, §10):** nothing between 22:00 and 08:00 in the
  thread's timezone. The exception is a change to a session starting within
  the next 12 hours, because a cancellation of tomorrow's 9:00 is worth waking
  up to. Held pushes go out at 08:00.
- **Email dedup.** Push and email are different channels, and Sjoerd asked
  for both. The digest is unchanged. Each is switched off separately: email
  with the existing switch, push per device. A participant who gets both sees
  the bell row once, because the push and the email point at the same row.
  Suppressing the email when a push was clicked is a possible later step, not
  in v1.
- **Who.** Exactly who already gets the bell row, enrolled participants
  included (`email_state 'none'`). They got the organiser's calendar email,
  but their phone didn't buzz; the bell is the point.

## 8. The payload: a title and a link, nothing else

```json
{ "title": "Moved: Choir rehearsal", "url": "/notifications", "tag": "thread:<uuid>" }
```

- **The title** is the kind's word plus the bell row's `subject`, which is a
  title the person could already see. No names, no dates, no prices, no body.
  It's written in the reader's language through `platformEmailLocale`, the
  same resolver the digest uses, from a small push catalog in the API
  (six locales).
- **The url** is a my.thread path, always `/notifications`. That page marks
  the rows read, which clears the dot.
- **Web Push payloads are end-to-end encrypted** (RFC 8291): Apple, Google
  and Mozilla carry them without being able to read them. Even so the payload
  stays minimal, because the lock screen is readable by anyone holding the
  phone.
- **A stricter alternative (§10):** a payload-less "tickle". The worker then
  fetches the newest unread rows itself, so nothing at all travels through a
  push service. It costs one round trip and a same-origin session in the
  worker. I recommend title + link, as the brief says, and offer the tickle
  only if Sjoerd wants lock screens to show only "my.thread: something
  changed".

## 9. iPhone and iPad: only once installed

- **On iOS and iPadOS 16.4 and later, web push works ONLY for a web app
  added to the Home Screen.** In a Safari tab, `PushManager` does not exist,
  so there's nothing to turn on.
- **The permission prompt** only appears from a tap inside the installed
  app.
- **What that means for a participant on an iPhone:** they install
  my.thread first (Share → Add to Home Screen; Help already has that guide),
  open it from the icon, and turn notifications on in the You tab. Without
  installing they keep the bell and the email, and nothing else.
- **Other platforms:**
  - Android (Chrome, Firefox, Edge) works in the browser, installed or not.
  - Mac Safari 16+ and the desktop browsers work in a tab.
- **The unsupported state in §6** says exactly this, with the link, so an
  iPhone user is told what to do rather than shown a button that does nothing.
